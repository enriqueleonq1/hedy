## 1. Recommendation: mixed mode

| Provider | Hedy chat (events + approvals) | Terminal tab and `hedy run` |
| --- | --- | --- |
| Claude Code | `claude -p` with stream-json both ways | interactive `claude` in a PTY |
| Codex | `codex app-server` (JSON-RPC over stdio) | interactive `codex` in a PTY |
| Gemini ⚠️ | `gemini --acp` (Agent Client Protocol) | interactive `gemini` in a PTY |
| Kimi / Gemini API | OpenAI-compatible HTTP (`ureq`) | — |

⚠️ Gemini CLI **no longer accepts personal Google accounts** (see section 5): it only
works with Code Assist Standard/Enterprise or a paid API key.

**Why mixed:**

- Hedy's own chat needs structured events and has to **ask for approval** before every
  command or edit. The three chosen modes let Hedy answer those requests; a PTY only
  gives screen text that cannot be translated reliably.
- The PTY is still needed: it is where the user does each CLI's **official login** the
  first time (each CLI shows its own wizard), and it is what `hedy run` uses.
- All three structured protocols belong to the official, unmodified CLIs.

**Why not ACP for everything:** Gemini speaks ACP natively, but Claude Code and Codex only
do it through third-party adapters (`claude-agent-acp`, `codex-acp`), which add another
layer and another binary. Their native protocols are more direct. If more ACP CLIs are
added later (Kimi Code, for instance), the Gemini ACP adapter is reused.

## 2. Account separation by folder

| CLI | Variable | Where the login lives (Linux) | Check without reading tokens |
| --- | --- | --- | --- |
| Claude Code | `CLAUDE_CONFIG_DIR` | `$CLAUDE_CONFIG_DIR/.credentials.json` (0600) | `claude auth status --json` (exit 0 = logged in, 1 = not) |
| Codex | `CODEX_HOME` (folder must exist) | `$CODEX_HOME/auth.json` with `cli_auth_credentials_store = "file"` | `codex login status` (exit 0 / 1) or app-server `account/read` |
| Gemini | `GEMINI_CLI_HOME` (creates `.gemini/` inside) | `$GEMINI_CLI_HOME/.gemini/oauth_creds.json` | No command. `google_accounts.json` holds the active email (no tokens) |

Tested with empty folders: each CLI wrote only inside its folder and did not touch
`~/.claude`, `~/.codex` or `~/.gemini`.

### Claude Code

- `CLAUDE_CONFIG_DIR` is documented (code.claude.com/docs/en/env-vars): it relocates
  settings, history, plugins, credentials, and also `.claude.json`.
- **Important detail:** without the variable Claude uses `~/.claude/` **and**
  `~/.claude.json` (outside the folder). With the variable it looks for
  `$CLAUDE_CONFIG_DIR/.claude.json`. So the existing account must **not** be "adopted"
  by setting `CLAUDE_CONFIG_DIR=~/.claude`: it would lose the MCP servers and settings in
  `~/.claude.json`. The existing account is registered in Hedy as the "default folder"
  and launched **without** the variable.
- On this machine the default account (`~/.claude`) is a **Team** subscription (work).
- Login into a new folder: `CLAUDE_CONFIG_DIR=<folder> claude auth login` (or `/login`
  inside `claude`). Both are the official flow.
- `claude auth status --json` returns `loggedIn`, `authMethod`, `subscriptionType`,
  `configDirectory`, and also email and organization. Hedy stores only what it needs.
- Doc caveat: two **Claude Console sign-ins without an API key** are not separated by
  folder. This does not affect subscription accounts.

### Codex

- `CODEX_HOME` is documented (learn.chatgpt.com/docs/config-file/environment-variables):
  config, auth, logs, sessions and skills.
- The login may go to `auth.json` or to the OS keyring. How the keyring entry is keyed per
  folder is **not documented**, so Hedy forces `cli_auth_credentials_store = "file"` in each
  account's `config.toml`. Codex writes and reads that file; Hedy never opens it.
- Login: `CODEX_HOME=<folder> codex login` (browser) or `codex login --device-auth`.

### Gemini

- `GEMINI_CLI_HOME` is documented (geminicli.com/docs/cli/enterprise and the bundled
  `docs/reference/configuration.md`).
- By default the Google login is stored in `oauth_creds.json` inside the folder.
- **Risk found in the code:** with `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE=true` the login
  goes to the keyring under service `gemini-cli-oauth` with a **fixed key**
  (`main-account`), the same for every folder. Two accounts would overwrite each other.
  Hedy removes that variable from the environment.

### Variables Hedy always removes (enforced in code)

If any of these reach the child process, the CLI uses that credential instead of the
folder's login, or bills through the API without warning:

- Claude: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`.
  The docs say that in `-p` mode the API key "is always used when present".
- Codex: `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`.
- Gemini: `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GENAI_USE_VERTEXAI`,
  `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE`.
- Leftovers from the session that launched Hedy: `CLAUDECODE`, `CLAUDE_CODE_*`,
  `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GEMINI_CLI_HOME`. Hedy then sets the variable for
  the selected account.

## 3. Claude Code

### Headless mode

```
claude -p --input-format stream-json --output-format stream-json --verbose \
       --permission-prompt-tool stdio --permission-mode manual [--model <alias>]
```

- Input (stdin, one line per message):
  `{"type":"user","message":{"role":"user","content":"..."},"parent_tool_use_id":null,"session_id":""}`.
  The process stays alive and accepts more messages; closing stdin ends it.
- Output: `system` (`init`, `compact_boundary`, `api_retry`, `status`, hooks…),
  `assistant`, `user` (tool results), `stream_event` (with `--include-partial-messages`),
  `rate_limit_event`, `result`, and `control_request` / `control_response`.
- `result` has `subtype` (`success`, `error_max_turns`, `error_during_execution`,
  `error_max_budget_usd`…), `is_error`, `duration_ms`, `num_turns`, `usage`, `modelUsage`,
  `total_cost_usd` and `permission_denials`. `total_cost_usd` is a **client-side
  estimate**; the docs warn it may not match the bill.
- Useful flags: `--resume <id>`, `--session-id <uuid>`, `--fork-session`,
  `--mcp-config` + `--strict-mcp-config`, `--append-system-prompt`, `--max-budget-usd`,
  `--include-hook-events`, `--no-session-persistence`.
- `--permission-mode` accepts `default` (alias `manual`), `acceptEdits`, `plan`, `auto`,
  `dontAsk` and `bypassPermissions`. `plan` fits the "plan" phase.

### Approvals: three routes

1. **Control protocol over stdio** (`--permission-prompt-tool stdio`). Claude sends a
   `control_request` with `subtype: "can_use_tool"`, `tool_name` and `input`. Hedy answers
   with a `control_response` `{"behavior":"allow","updatedInput":…}` or
   `{"behavior":"deny","message":…}`. The official Agent SDK uses it. Tested: the
   `initialize` handshake answers. **Risk:** only partly documented (no public spec).
2. **MCP permission tool** (`--permission-prompt-tool mcp__hedy__approve`). Officially
   documented: the tool returns one text block with `{"behavior":"allow"}` or
   `{"behavior":"deny","message":"…"}`. Requires Hedy to serve a small MCP (it will need
   one for memory anyway).
3. **`PermissionRequest` hook.** Documented, works in `-p`.

**Proposed decision:** use route 1 and keep route 2 as a fallback behind the same port.
If an update breaks route 1, it is swapped without touching the UI. "Allow for this chat"
is remembered by Hedy per session.

### Usage and limits

- `rate_limit_event` in the stream: `status` (`allowed`, `allowed_warning`, `rejected`),
  `resetsAt` and `utilization`. The docs do not say which window (5 h or weekly)
  `utilization` refers to. **Unverified** with a real account yet.
- The `statusLine` command receives `rate_limits.five_hour` and `rate_limits.seven_day`
  with percentage and reset time, only on Pro/Max/Ultra and after the first response.
  Option for PTY sessions: Hedy registers its own `statusLine` command (via `--settings`)
  that only records those percentages.
- No rate-limit metrics via OpenTelemetry.
- **Plan usage through `/usage` (verified Nov 14, 2026, Claude Code 2.1.306, Team plan).**
  Details and the other providers in §20.

### Does programmatic use draw from a different pool? (phase 0 question)

Source: support.claude.com/en/articles/15036540 ("Use the Claude Agent SDK with your Claude plan").

- **June 15, 2026:** Anthropic **paused** the announced change: "Claude Agent SDK,
  `claude -p`, and third-party app usage still draw from your subscription limits."
- **October 7, 2026:** Max, Ultra and Team plans include monthly API credits. Those credits
  only apply when the SDK or `claude -p` run with an **API key** from the linked Console
  organization. With a subscription login, `claude -p` still draws from plan limits.
- **Conclusion:** today `claude -p` with a subscription login draws from the **same pool**
  as interactive use. Headless and PTY cost the same.
- The credit amounts are **unverified** (not in the article).
- This changed twice this year; Hedy will show the source on the accounts screen and we
  re-check it every phase.

### Policy note

The Agent SDK docs say: "Unless previously approved, Anthropic does not allow third party
developers to offer claude.ai login or rate limits for their products." Hedy is a
**personal, local** tool that launches the official binary with the login the user did
themselves; it does not offer claude.ai login to third parties. If it is ever distributed
to other people, this must be reviewed first.

## 4. Codex

Docs moved from `developers.openai.com/codex` to `learn.chatgpt.com/docs`.

### App server (recommended for the chat)

- `codex app-server --listen stdio://`: JSON-RPC 2.0, one JSON line per message. OpenAI
  presents it as "the interface Codex uses to power rich clients". Marked experimental;
  without `capabilities.experimentalApi` the client stays on the stable surface.
- Flow: `initialize` → `initialized` notification → `thread/start` (`cwd`,
  `approvalPolicy`, `sandbox`, `model`) → `turn/start` (`threadId`,
  `input: [{type:"text", text}]`).
- Notifications: `item/started`, `item/completed` (types `agentMessage`, `plan`,
  `reasoning`, `commandExecution`, `fileChange`, `mcpToolCall`…),
  `item/agentMessage/delta`, `turn/plan/updated`, `turn/diff/updated`,
  `thread/tokenUsage/updated`, `account/rateLimits/updated`, `turn/completed`, `error`.
- **Approvals:** the server sends `item/commandExecution/requestApproval` and
  `item/fileChange/requestApproval`. Answers `accept` / `acceptForSession` / `decline` map
  1:1 to **Allow / Allow for this chat / Deny**.
- **Limits:** `account/rateLimits/read` returns `primary` and `secondary`, each with
  `usedPercent`, `windowDurationMins` and `resetsAt`. Hedy reads `windowDurationMins`
  instead of assuming which window is 5 h and which is weekly. The account cards read it
  (§20).
- `codex app-server generate-json-schema --out <dir>` generates the exact schema for that
  version. Hedy will pin the supported version and generate Rust types from it.
- Tested: `initialize` and `account/read` work without login (`requiresOpenaiAuth: true`);
  `account/rateLimits/read` returns "authentication required".

### Alternative: `codex exec --json`

JSONL with `thread.started`, `turn.started`, `item.*`, `turn.completed` (with `usage`),
`turn.failed` and `error`. Good for single-turn jobs, but it **cannot ask for approvals**
(fixed policies only) and has no limits. `--full-auto` no longer exists.

### Billing

"Local messages and cloud chats share your plan's usage allowance." No separate pool is
documented for `exec` or the app server; everything points to the same one.

## 5. Gemini

### ⚠️ Gemini CLI no longer works with personal accounts

- Since **June 18, 2026**, Gemini CLI stopped serving consumer accounts: free tier,
  Google AI Pro and Google AI Ultra. Google replaced it with **Antigravity CLI** (`agy`).
  Sources: developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli
  (May 19, 2026) and the banner on every geminicli.com page. The 0.68.0 binary itself
  contains messages pointing to Antigravity CLI.
- **Still works** with Gemini Code Assist Standard/Enterprise and paid Gemini API keys.
  Vertex AI and free API keys: **unverified** (sources conflict).
- **Antigravity CLI** has `agy acp`, but it stores the login in the **OS keyring** and has
  no documented variable to relocate its folder. That rules out several accounts separated
  by folder: for now it only fits **one personal account** per machine.
- Gemini CLI is still maintained (0.68.0 on Nov 10; 0.69 in preview).

### What was verified about Gemini CLI

- Official package `@google/gemini-cli` (0.68.0). Login: "Log in with Google"
  (`oauth-personal`), Gemini API key, or Vertex AI.
- **ACP** (`gemini --acp`; `--experimental-acp` is deprecated): JSON-RPC over stdio.
  Methods `initialize` (returns `authMethods`), `authenticate`, `session/new`,
  `session/load`, `session/prompt`, `session/cancel`, `session/set_mode`. The agent sends
  `session/update` notifications (`agent_message_chunk`, `tool_call`, `tool_call_update`,
  `plan`…) and asks for approval with `session/request_permission`, offering
  `allow_once` / `allow_always` / `reject_once`. They map 1:1 to Hedy's approval cards.
- Tested: `initialize` returns the auth methods; `session/new` without login returns
  "Gemini API key is missing or not configured".
- **Headless** (`gemini -p … -o stream-json`): events `init`, `message`, `tool_use`,
  `tool_result`, `error`, `result` (with per-model stats), all with `type` and
  `timestamp`. It cannot ask for approvals, only `--approval-mode` (`default`,
  `auto_edit`, `yolo`, `plan`). Fits `hedy ask`. Exit codes: 0, 1 (error), 42 (bad
  input), 53 (turn limit).
- In a PTY, the first run shows "Waiting for authentication…" (may open the browser) and
  the trust-folder question.
- **Quota:** 1,500–2,000 requests/day depending on the plan (Code Assist Standard /
  Enterprise). There is no programmatic way to read the remaining quota (`/stats model`
  is interactive only). Hedy will count requests and show it as an **estimate**.
- MCP: `mcpServers` in `settings.json` or `gemini mcp add --scope user|project`. The context
  file can be renamed with `context.fileName` (e.g. to `AGENTS.md`).
- **Terms:** using the Code Assist service with Gemini CLI's login from third-party
  software (i.e. bypassing the CLI) is prohibited and may lead to suspension. Launching the
  official, unmodified CLI, as Hedy does, is not prohibited, though not explicitly allowed.

### Gemini through the API (Kimi-style provider)

- OpenAI-compatible endpoint: `https://generativelanguage.googleapis.com/v1beta/openai/`
  with `Authorization: Bearer <GEMINI_API_KEY>`. Supports `tools`, `stream` and
  `stream_options.include_usage`. Google still labels it beta.
- Coding models: `gemini-4-carbon` ("built for complex software engineering"),
  `gemini-4-hydrogen` ("everyday coding and agentic workflows") and `gemini-3.8-flash`.
  The 2.5 family is retired on December 1, 2026.
- Gemini then works like Kimi: an API key in the keyring and the shared HTTP adapter.
  **This is the simplest and safest way to add Gemini with a personal account.**

## 6. Kimi

- Docs moved to `platform.kimi.ai` (formerly `platform.moonshot.ai`).
- OpenAI-compatible API: `POST https://api.moonshot.ai/v1/chat/completions` (China:
  `api.moonshot.cn`). Supports `tools`, `stream` and `stream_options.include_usage`
  (total usage in the last chunk).
- **Current models:** `kimi-k3.1-pro` (most capable, 1M context),
  `kimi-k3.1-pro-highspeed` and `kimi-k3`. The `kimi-k2.*` family is deprecated or retires
  in December 2026. K3 models always "think" and take `reasoning_effort`.
- There is also an Anthropic-compatible endpoint (`https://api.moonshot.ai/anthropic`).
- **Kimi Code** (subscription) has its own endpoints and keys
  (`https://api.kimi.ai/coding/v1`) and a new official CLI, `MoonshotAI/kimi-code`, which
  speaks ACP (`kimi acp`). The old `kimi-cli` is archived.

## 7. PTY (`portable-pty`)

- Works with all three CLIs. On first run each shows its wizard: Claude asks for a theme
  and then login, Codex offers "Sign in with ChatGPT / Device Code / API key", and Gemini
  asks for login and folder trust.
- Hedy **does not automate** those wizards: the user logs in from the Terminal tab. That
  keeps rule 1.
- `portable-pty` starts in `$HOME` unless told otherwise: always pass `cwd`.
- PTY session state is not read by scraping the screen. Claude hooks and `statusLine`
  write to a Hedy socket instead.

## 8. Changes from the original spec

1. **Gemini** added as a provider (requested during phase 0). Gemini CLI only works with
   Code Assist Standard/Enterprise or a paid API key. For a personal account, the practical
   route is the Gemini API over HTTP, like Kimi.
2. **Kimi:** model names changed to `kimi-k3.x`. Two ways to use it: API (pay as you go)
   or Kimi Code (subscription, with official CLI and ACP).
3. **Codex:** recommended mode is the app server, not `exec`, because `exec` cannot ask for
   approvals.
4. **Claude:** chat approvals rely on a partly documented protocol. Mitigation: fallback to
   the MCP permission tool.
5. **Anthropic policy** on claude.ai login in third-party products: no effect while Hedy is
   for personal use.
6. **Protected projects (rule 4)** are now **opt-in per project and off by default**
   (user decision, Nov 13, 2026). No account is ever blocked by default; when a project is
   marked protected, it only uses its assigned account and that account is not offered
   elsewhere.
7. **Language:** code, identifiers, folders, docs and commits in English. User-facing text
   stays in Spanish.

## 9. Phase 2 decisions

- **UI framework: React 19** instead of Svelte 5 (user decision, Nov 13, 2026): wider
  ecosystem; the performance difference is not noticeable here, where WebKitGTK and
  xterm.js dominate. Server state with TanStack Query.
- **Visual reference:** `identidad visual/` is the source of truth for layout, sizes and
  the mascot. Where it differs from the written spec, the images win: the top droplet
  floats above the halo, and there is a resting pose (`idle`, "En espera") besides the
  four states.
- **Terminal:** PTY sessions in `hedy-core::adapters::PtySession`, with the same
  environment rules as every other launch. Login from the app runs the official flow in
  the integrated terminal.
- **CLI ↔ app:** both use the same SQLite file, so they already see the same state. The
  Unix socket from the spec is only needed for live events and arrives with phase 3.

## 10. Phase 3: tasks (verified against Claude Code 2.1.306)

`cargo run -p hedy-core --example smoke_task -- haiku` runs a real task end to end in a
throwaway repo (plan → approval → permission → diff → accept + merge); `-- haiku env`
checks that `.env` stays unread. Both passed on Nov 13, 2026.

- **Flow:** a `Project` task gets a worktree in `.hedy/worktrees/<id>` (excluded through
  `.git/info/exclude`) on branch `hedy/<slug>-<id>`, forked from the current commit.
  Accept = commit in the worktree + `git merge` in the main checkout, only if it is on the
  base branch and clean (otherwise the commit stays on the branch and Hedy says why).
- **Plan first:** `--permission-mode plan`. The plan arrives as a `can_use_tool` request
  for `ExitPlanMode` (`input.plan`); allowing it lets Claude leave plan mode and
  implement in the same turn; denying it with the user's feedback makes it re-plan.
- **Permission requests** arrive as `control_request` / `can_use_tool` and are answered
  with `control_response` (`allow` + `updatedInput`, or `deny` + `message`). Confirmed.
- **Claude does not ask for everything.** In real runs it read files, ran read-only shell
  commands (`wc`, `cat`) and wrote its plan to `~/.claude/plans/` without a request. So:
  - Protected files are also passed as Claude Code's own `permissions.deny` rules
    (`--settings`, `Read(**/.env)`, `Edit(**/.env)`...), which the CLI enforces itself.
    Verified: the `.env` read was blocked by the CLI.
  - A **`PreToolUse` hook** (also in `--settings`) runs the same protected-file rules on
    every Bash/Read/Edit/Write call, including the ones Claude Code runs without asking.
    The app binary serves it (`hedy-app hook pre-tool-use`). Verified: `cat .env` through
    Bash was blocked by the hook (`smoke_task -- haiku bash`).
- **Dependencies in the worktree:** git-ignored `node_modules`, `.venv`, `venv` and
  `vendor` are symlinked from the main checkout (and excluded locally, since git does not
  treat a symlink as an ignored directory), so builds and tests work without reinstalling.
  `.env` files are deliberately not shared: a task never has the secrets at hand.
- **Preview:** the "Vista previa" tab embeds a local dev server (localhost / 127.0.0.1
  only, enforced in the UI and in the CSP `frame-src`).
- **Pregunta / Research:** no worktree; edit tools disabled with `--disallowedTools`;
  Research also allows `WebSearch,WebFetch`.
- **Usage:** each `result` gives tokens and a cost *estimate*; `rate_limit_event` gave
  `status` and `resetsAt` but `utilization: null` on the Team plan. Account cards show the
  reported status ("dentro del límite / cerca / alcanzado") and renewal time, the % only
  when reported, and Hedy's own token count labelled as such. Since §20 the cards show
  the plan's windows read from `/usage` instead, which also counts what the user runs
  outside Hedy (Claude Code, the VS Code extension).

## 11. Phase 4: several providers

- **Models per phase.** Each project can assign plan, implement, tests and review to an
  account and model (`projects.phases`). A task runs them as a pipeline. If the same
  agent plans and implements, it continues in the same session (Claude: allow
  `ExitPlanMode`). If not, the planner is told the plan was handed off, and the next agent
  starts with the request, the approved plan and a summary of what was done. Tests and
  review only run when configured. A model picked in the composer overrides all phases
  ("Solo opus"). Protected projects can only assign their own account.
- **Codex** runs through `codex app-server`. Plan-first is emulated: a turn with
  `sandboxPolicy: readOnly` that only proposes a plan, then a `workspaceWrite` turn once
  approved. Approvals map to `accept` / `decline`. Multi-file patches are checked file by
  file. Codex has no equivalent of Claude's deny rules or hook, so a task with Codex
  **always runs in a worktree** (also for questions), where `.env` does not exist.
- **Kimi and Gemini by API key** run on an OpenAI-compatible agent. Hedy gives the model
  six tools (list, read, search, write, edit, run) and runs them itself, so every rule is
  enforced natively: reads stay inside the task folder and never touch protected files;
  writes and commands always go through permission cards. Defaults:
  `kimi-k3.1-pro` at `api.moonshot.ai/v1`, `gemini-4-hydrogen` at
  `generativelanguage.googleapis.com/v1beta/openai`. The URLs can be changed in Ajustes
  (Kimi China, Kimi Code). Gemini CLI (Code Assist only) is not wired in.
- **Limits (rule 3).** Rate-limit reports become a warning card once per level (≥ 90 % or
  `allowed_warning`, then reached). Hedy never switches accounts by itself. The card offers
  to wait, or to hand the task over to **another provider or an API-key account**, never
  another subscription of the same provider, and never in a protected project. A handoff
  starts the new agent with the request, the plan and the files changed so far.
- **Verification.** Claude is verified against the real CLI (`smoke_task`). Codex is
  tested against a fake `app-server` that follows the schema generated by Codex 0.169.0,
  and the API agent against a local fake HTTP server. A real check of both still needs a
  ChatGPT login and a Kimi/Gemini key.

## 12. Phase 5: shared memory and code map

- **Storage.** Notes live in Hedy's SQLite database (`notes` + an FTS5 index with
  `unicode61 remove_diacritics 2`, so "recordatorio" finds "recordatorios" and accents do
  not matter). Each note has a project (or none: a global note), a category (decision,
  convention, rule, preference), an author, a status and use counts (`note_uses`, per
  task). The database runs in WAL mode with a busy timeout because the memory server opens
  it from another process.
- **Rule 6.** Agents only read approved notes. What they write is always a proposal
  (`memory_propose`); the user approves, edits or rejects it in the memory screen. Notes
  written by the user are approved right away.
- **Protected projects** neither read nor show global notes, and their notes never appear
  elsewhere.
- **How agents read it.** One `hedy-memory` server per run, scoped to the project, task and
  agent, with `memory_search`, `memory_get`, `memory_topics` and `memory_propose` (see
  below). It is an rmcp stdio server
  served by the app binary itself (`hedy-app memory-mcp --data-dir … --project …`), like the
  `PreToolUse` hook. Claude gets it with `--mcp-config` (JSON), its tools pre-allowed with
  `--allowedTools mcp__hedy-memory`, plus guidance in `--append-system-prompt`. The
  account's own MCP config is left alone. Codex gets it with `-c mcp_servers.<name>.*`
  overrides (TOML values) and the guidance as `developerInstructions`; this is **not yet
  verified against a real Codex**. The API agent gets the same tools natively.
  Verified for real: Claude Code (haiku) read a note through the server, the use was
  recorded with the task, and its proposal waited for approval.
- **Topics, similar notes and progressive reading** (ideas taken from Engram, gentle-ai's
  memory; nothing of it is used as code):
  - A note may have a `topic`: a stable lowercase slug path such as `arquitectura/pagos`
    (accents dropped, anything else becomes a dash; `normalize_topic`). Columns `topic`
    and `updated_at` were added in a migration, and `notes_fts` was rebuilt to index the
    topic too.
  - A proposal under the topic of an approved note in the same scope is a *change* to
    that note: the memory screen and `hedy memory list` show the old and the new text.
    Approving it replaces the approved note's text, category and author in place (same
    id, creation date and uses; `updated_at` records when) and deletes the proposal.
    Rejecting it deletes the proposal and nothing else changes. Until then agents keep
    reading the approved version (rule 6 holds: they only ever propose).
  - Next to each proposal, up to three approved notes that look like it: FTS5 finds
    candidates by the proposal's key words (accents and a plural "s" folded) and a local
    word-overlap check keeps the close ones. No AI, no network. It is labelled "parecida
    a" / "similar to", never a contradiction, and offers keep both, replace that one
    (`replace_note`: the proposal becomes the new version of that note) or discard.
  - MCP tools: `memory_search` now returns one compact line per note
    (`- #id [category · scope] topic: first line…`, cut to 140 characters);
    `memory_get` (`id` or `topic`) returns one whole note; `memory_topics` lists the
    topics; `memory_propose` takes an optional `topic`. The old calls (search with a
    query, propose with text and category) keep working. The API agent has the same four
    tools.
  - End-of-task summary: agents that may change the project (not review, ask or research)
    are told to propose, before their final answer, one short note with the lasting
    decisions they made, and to stay quiet if there were none. It is only guidance; it is
    still a proposal the user approves.
  - CLI: `hedy memory` with `list` (default), `approve <id>` and
    `reject <id>`.
- **"Quién la lee"**: the project's account and the accounts in its phases. Turning one off
  (`projects.memory_off`) starts that agent without the memory.
- **Contradictions** come from a local heuristic, with no AI involved: the notes share most
  of their words and one is negated (no, nunca, evitar…) or only a number differs. The user
  keeps one note or marks both as valid (`note_dismissed_pairs`). **Para revisar**:
  approved notes unused for 60 days.
- **Code map: codebase-memory-mcp** (DeusData, MIT). It is a single static binary with no
  runtime and no telemetry. Its index stays in `~/.cache/codebase-memory-mcp`, and
  `CBM_ALLOWED_ROOT` can confine it to a folder. Codegraph was the alternative; it needs
  Node and a per-repo index directory inside the project. Hedy only installs and
  registers it:
  - "Instalar" in Ajustes runs the official script (which checks the download's sha256)
    in the integrated terminal, with `--skip-config`, so it does not edit any CLI's
    config.
  - Once it is found (on `PATH` or in `~/.local/bin`), a switch registers it in every run
    as `codebase-memory`, with `CBM_ALLOWED_ROOT` set to the project.

## 15. Languages, first run and installation

- **Two languages: Spanish and English.** The setting `ui.language` is `system`, `es` or
  `en` (default `system`). `system` reads `HEDY_LANGUAGE`, then `LC_ALL`,
  `LC_MESSAGES` and `LANG`; anything that is not Spanish falls back to English in the
  core and the CLI. The app resolves `system` with `navigator.language`.
- **Rust.** One process-wide language (`hedy_core::i18n`), set from the setting when the
  app or the CLI starts. Texts are written in place with `tr!("es {x}", "en {x}")`, so
  both languages sit side by side and a missing one does not compile. Errors keep
  `thiserror` with `#[error("{}", self.message())]`. Every child process (Claude's
  `PreToolUse` hook, the memory server) gets `HEDY_LANGUAGE`, so its messages match.
- **Agents reply in the user's language.** Every system prompt Hedy adds starts with
  `prompts::reply_language()`. The hook's denial text exists in both languages, and the
  Claude adapter recognises either one.
- **React.** `I18nProvider` / `useT()` with flat dotted keys and `{param}`. Spanish is
  the source; each area file types its English table against the Spanish one. Tests
  render in Spanish unless they wrap with `I18nProvider setting="en"`.
- **First run.** While `ui.onboarded` is not `true` the app shows a six-step guide
  (welcome and language, what Hedy is, accounts, safety, memory, ready). The accounts
  step calls `detect_clis`: whether each CLI is installed and whether its default
  folder is logged in (the CLI's own status command; Hedy reads no tokens). "Use this
  session" registers the default folder; "Log in" opens the official login in the
  terminal panel. Settings can show the guide again. Examples in the guide are generic,
  not about programming.
- **Installation (Arch / CachyOS).** `packaging/arch/PKGBUILD` builds the app without
  Tauri's bundler (`tauri build --no-bundle`) and the CLI, and installs `hedy-app`,
  `hedy`, the desktop entry `hedy-app.desktop` (named after the Wayland app id, so the
  dock matches the window) and the icons. Debian/Fedora/macOS bundles can come from
  `tauri build` later.

## 16. Health check (`hedy doctor`)

- **Read-only, official commands only.** `hedy doctor` (Tauri
  command `doctor`) runs each CLI's `--version` (5 s timeout) and the same official login
  status commands as `login_state`; it never opens a token file and never prints a key or
  a variable's value. The one thing it writes is the last version seen per CLI
  (setting `doctor.cli_version.<provider>`).
- **CLIs** (respecting `binary.<provider>`): missing is info, or an error when an account
  uses it or `binary.<provider>` points nowhere. A version different from the last run
  is a warning unless it is the verified one; versions in the table at the top live in
  `Provider::verified_version()` (Kimi Code and Antigravity: not verified yet).
- **Accounts:** managed folder exists, login state (signed out is a warning with
  `hedy account login <id>`), API keys only by presence in the keyring. Also the default
  account (missing, removed, or reserved by a protected project).
- **Hedy:** data folder writable, SQLite `PRAGMA quick_check`, git, the memory MCP server /
  `PreToolUse` hook entry point (the app binary; info from the `hedy` command when the
  app is not on `PATH`), the code-map program if set, project folders that are gone.
- **Environment:** names of the variables Hedy strips (§2) that are set, as info. What a
  Claude Code session leaves behind (`CLAUDECODE`, `CLAUDE_CODE_*` except the credential
  and billing ones) is one counted line, so a stray API key stands out.
- Levels: ok, info, warning, error. The CLI exits with 1 when there is an error. CLI
  and account checks run in parallel, like `detect_clis`.

## 17. Task board and desktop notifications

- **Task board ("Actividad" / "Activity", `hedy tasks`).** `Hedy::activity()`
  lists every project's running and waiting tasks plus those with activity in the last
  24 h (at most 30 finished ones). The state is derived from the task and its history,
  never stored (`domain::task_state`): a plan or a permission card waiting, a limit
  reached (until the user writes or a handoff starts a phase), working, changes to
  review, answered, accepted, failed, discarded. What needs the user comes first. The app
  refreshes it from the task events it already receives; a row opens the task in its
  project's workspace, and the navigation shows how many tasks need the user.
- **Notices.** The core sends a `Notice` through the `TaskEvents` port when a task starts
  waiting for a plan or a permission (once, not per card), finishes, fails or reaches
  its limit, unless `ui.notifications` is `off` (`on` by default). The text names only
  the agent and the project ("Claude necesita tu aprobación · tienda-online"): never the
  prompt, commands, file contents or secrets. A reached limit is only reported; Hedy
  never switches accounts.
- **Plugin.** Official `tauri-plugin-notification` 2.8.1 (latest stable on crates.io and
  npm in November 2026). The app shows notices only while its window is not focused.
  Notifications are sent from Rust only, so the webview gets no `notification:*`
  permission in `capabilities/` (least privilege; capabilities only gate calls from the
  frontend). Linux and the BSDs use the Desktop Notifications D-Bus service; macOS
  the Notification Center through `notify-rust`; all local.
- **Click to open.** On desktop, 2.8 reports a click on a notification (`tap`) to
  `Notification::on_action` handlers registered before it was shown. Hedy registers one
  at start-up: it unminimizes, shows and focuses the window and emits `open-task` with
  the task id and project, which the UI turns into its workspace. Linux needs a
  notification server that advertises the `actions` capability (KDE Plasma 6 does,
  checked with `GetCapabilities`); without it the notification is only shown. Windows
  reports clicks only while the toast is on screen. Not tried by hand on macOS, where a
  development build may not be allowed to notify until the app is bundled and signed.

## 18. Learned skills

Idea taken from Hermes Agent's self-created skills, with one change: agents only
**propose**, the user approves (rule 6 applies to skills as to notes). Checked on
November 14, 2026 against the official docs below; nothing here modifies a CLI.

**Where each CLI reads project skills** (a folder `<name>/SKILL.md` with YAML frontmatter,
the [Agent Skills format](https://agentskills.io/specification): `name` of 1–64
lowercase letters, digits and single dashes, equal to the folder name; `description` of
1–1024 characters):

| CLI | Project folder | Discovery | Source |
|---|---|---|---|
| Claude Code | `.claude/skills/` | cwd and parents up to the repo root; in a linked worktree only up to the worktree root, but since 2.1.277 a worktree **without** its own `.claude/skills` reads the main checkout's. `claude -p` loads skills (not with `--bare`) | [skills](https://code.claude.com/docs/en/skills), [worktrees](https://code.claude.com/docs/en/worktrees), [headless](https://code.claude.com/docs/en/headless) |
| Codex | `.agents/skills/` | every folder from cwd up to the repo root; also via `skills/list` in the app server | [build skills](https://learn.chatgpt.com/docs/build-skills.md), [app server](https://learn.chatgpt.com/docs/app-server.md) |
| Gemini CLI | `.gemini/skills/` or `.agents/skills/` (the alias wins) | the current folder | [skills](https://geminicli.com/docs/cli/skills.md) |
| Kimi Code | `.kimi-code/skills/` or `.agents/skills/` | the project root (nearest `.git` going up) | [skills](https://moonshotai.github.io/kimi-code/en/customization/skills) |
| Antigravity | `.agents/skills/` | the start folder up to the repo root | [skills](https://www.antigravity.google/docs/skills?tab=cli) |

- **Storage.** Table `skills` (the 8th migration): project (NULL = global), name, description,
  body, status (`proposed` / `approved`), author, created/updated, source task. A
  proposal with the name of an approved skill in the same scope is a proposed
  **update** (shown as before/after, the steps as a line diff); approving it replaces
  the description, steps and author in place (same id); rejecting deletes it. Same
  pattern as note topics (§12), separate concept.
- **Proposing.** `skill_propose {name, description, body}` in the memory MCP server and
  the API agent. The name is turned into a slug; Claude's reserved names (`synced`,
  `anthropic-skills`) are refused; bodies up to 20,000 characters. A local heuristic
  refuses text that looks like a secret (known key prefixes such as `sk-`, `ghp_`,
  `AKIA`, `AIza`; private keys; JWTs; `TOKEN=value` assignments of secret-looking names
  that are not placeholders such as `$TOKEN` or `<your key>`), with an error that never
  repeats the value. The guidance asks only agents that may change the project, at the
  end of a successful task, for at most one skill, and only for a non-obvious, reusable
  procedure; otherwise they stay quiet.
- **Reading.** Every agent with the memory server (and the API agent) gets
  `skill_list` (one line per approved skill: name, scope, when to use it) and
  `skill_get {name}` (the whole skill), progressive like `memory_search` /
  `memory_get`. Claude already pre-allows `mcp__hedy-memory`. Turning the memory off for
  an account also turns these tools off; the native files below stay.
- **Native files.** Approving a project skill writes `.claude/skills/<name>/SKILL.md` and
  `.agents/skills/<name>/SKILL.md` (one copy each, no symlinks: only Codex documents
  following them) in the project and in the worktrees of its open tasks, and new
  worktrees get them when they are created. Each folder is added to
  `.git/info/exclude` (`/.claude/skills/<name>/`, `/.agents/skills/<name>/`, anchored, so
  it also covers worktrees) before the file is written, so a task's diff and commit
  never include them. Editing, renaming, moving to global or deleting rewrites or
  removes them (and empty folders left behind); the exclude lines stay, harmless.
  - **Claude in worktrees:** a worktree only gets Claude's copy when it already has a
    `.claude/skills` folder (committed by the team). Otherwise Claude Code reads the
    main checkout's, which also keeps the user's own uncommitted skills working there;
    writing a `.claude/skills` into the worktree would hide them.
  - **Never overwrite the user's files:** every file Hedy writes carries the line
    `<!-- hedy: managed skill -->`; a file at that path without it is the user's and is
    skipped (the UI and `hedy skills` warn), and never deleted.
- **Global skills: only through the MCP tools.** Hedy does not write into
  `~/.claude/skills`, `$CODEX_HOME`, `~/.agents/skills` or any account folder: rule 1 says
  Hedy only picks the folder at launch, and `~/.agents/skills` would be shared by every
  account. Protected projects neither see nor create global skills.
- **UI and CLI.** A "Habilidades" / "Skills" tab in the memory screen (`#k=<path>`) and
  `hedy skills` with `list`, `show <name>`, `approve <id>`,
  `reject <id>` and `remove <name>`.
- **Not verified with the real CLIs yet:** that Codex, Gemini CLI, Kimi Code and
  Antigravity load `.agents/skills` in ACP / app-server mode (their docs describe the
  interactive CLI); that Codex and Kimi stop the root search at a linked worktree's
  `.git` file (likely); that Gemini CLI loads skills in an untrusted folder. Claude
  Code's `--bare`, announced as the future default for `-p`, would skip native skills;
  the MCP tools still work then.

## 19. Writing while the agent works, and prompt templates

Verified against the official docs in November 2026 (Agent SDK "Streaming Input",
`code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode`).

- **Queue, not mid-turn injection.** A message written while the agent works is queued
  ("En cola" / "Queued") and goes as the **next user turn of the same session** (same
  account, same phase) when the turn ends (`Finished`). The Claude docs say streaming
  input takes "multiple messages that process sequentially", but nothing about how a
  message written mid-turn mixes with a waiting `ExitPlanMode` request or a permission
  prompt; ACP v1 runs one `session/prompt` at a time; Codex's app server has no
  documented way to add input to a running turn. So Hedy always waits for the turn
  boundary, for every provider, and never writes to a CLI's stdin mid-turn.
- **One turn.** Every message waiting when the turn ends goes together, in order,
  separated by a blank line (`domain::queue::join_queued`): the same for every adapter,
  and the agent answers everything at once.
- **Decisions first.** Nothing is delivered while a plan or permission card waits
  (status `waitingApproval` or open requests in the session). The user answers, the
  agent's turn ends, then the queue goes. A queued message is delivered before the
  next phase starts, so it reaches the agent it was written to.
- **On hold.** When the task fails, the user stops it or the account reaches its limit,
  the queue is kept and marked held (`failed`, `stopped`, `limit`); the chat says why.
  Held messages are only sent when the user presses "Enviar ahora" (to the task's
  current account, resuming its session if needed). After a limit nothing goes out by
  itself and nothing moves to another account (rule 3); a handoff does not take the held
  queue along. Accepting or discarding a task drops its queue.
- **Storage.** Table `queued_messages` (task, text, time, `held`), so a restart keeps
  the queue; after a restart the process is gone and the queue waits for "Enviar
  ahora". `hedy_core` sends `TaskEvents::queue_changed`; the app emits `task-queue`.
  The task board shows "N en cola".
- **Prompt templates.** Global or per project, stored in SQLite (`prompt_templates`),
  never in the repository. A placeholder is `{name}`: letters (accents included),
  digits, `_` or `-`, at most 40, no spaces; `{ }`, `{}` or JSON stay plain text. In the
  composer, `/` at the start opens a listbox (filtered as you type, arrow keys,
  `aria-activedescendant`); choosing a template with placeholders asks for each one in a
  small form, then the text goes into the composer to be edited and sent. Names are
  unique per scope; a project template wins over a global one with the same name.
- **Built-in examples.** Five generic, bilingual examples live in the code
  (`domain::template::builtins`) and follow the current language; editing or deleting
  one stores a row for it, and "Restaurar ejemplos" removes those rows.
- **CLI.** `hedy template` lists, adds (`--project` for the current
  project) and removes templates. There is no task-launch command in the CLI (`hedy run`
  opens the official CLI), so there is no `--template` flag yet.
- **Not verified** with a real CLI: delivery at the turn boundary is tested with the
  in-memory agent double and in the UI with `MockApi`; the adapters were not changed.

## 20. Plan usage per account (Nov 14, 2026)

Account cards, the sidebar, the header chips and `hedy status` show how much of each
plan's limits is used, like `/usage` does, including what the user ran outside Hedy.
Each provider has its own source behind one model (`domain/plan_usage.rs`,
`PlanUsage`): windows of kind session (5 h), week, day or other (with their length),
optionally limited to one model, each with a percentage, the reset as the source wrote
it, and the reset as a Unix time when it can be worked out.

### Claude Code: `claude -p /usage` (verified)

```
claude -p /usage --output-format json --no-session-persistence --safe-mode
```

- Official docs (code.claude.com/docs/en/commands): `/usage` "Show session cost, plan
  usage limits, and activity stats", with a breakdown on Pro, Max, Ultra, Team and
  Enterprise. Unlike the `statusLine` `rate_limits` field (Pro/Max/Ultra only), it works
  on the Team plan.
- In print mode the built-in command runs **locally**: the JSON `result` came with
  `num_turns: 0`, `total_cost_usd: 0`, every token count 0, `duration_api_ms: 0` and
  `local_command: "usage"`. It takes 6–8 s (it starts Claude Code).
- `--safe-mode` (hooks, MCP servers, plugins and custom commands off; auth works
  normally) and `--no-session-persistence` (nothing added to `/resume`) were checked to
  give the same answer. Launch as every other: the account's `CLAUDE_CONFIG_DIR` (none
  for the default folder), `binary.claude` respected, credential variables stripped.
- **Zero-cost guard.** If an answer ever shows `num_turns > 0`, a cost above 0 or any
  token, Hedy stores that CLI version in `plan_usage.spends_tokens.claude` and stops
  asking it (`--version` is checked before each attempt; another version is tried
  again). The UI then says so; `hedy doctor` warns.
- **The limits are only text** (no documented JSON for them), in English even with
  `LANG=es_ES.UTF-8`:

  ```
  Current session: 34% used · resets Nov 14, 7pm (America/Caracas)
  Current week (all models): 29% used · resets Nov 20, 12am (America/Caracas)
  Current week (Fable): 0% used · resets Nov 20, 12am (America/Caracas)
  ```

  Parser rules (fragile by nature, so tolerant): a line counts when the text before its
  first `N%` (decimals with `.` or `,`) names a window (`session`/`5-hour`, `week`/`7-day`,
  `day`); a parenthesis names the model, `all models` (or none) means every model; the
  first window of each kind and model wins; the reset is whatever follows `resets`:
  `Nov 14, 7pm (Zone)`, `Dec 1 at 9:30am`, `7pm`, `19:00 (UTC)` or `in 3 hr` / `in 2h 30m`.
  Anything else keeps the text and no time; a reply without any window is "no data", never
  an error. The IANA zone is resolved with the system time-zone database (`jiff`, behind
  the `Clock` port), the year being the next occurrence. The "What's contributing"
  section is ignored. Verified format: Claude Code 2.1.306.
- `rate_limit_event` reports from Hedy's own tasks are merged when newer than the
  reading and carrying a percentage: they update the window that renews at the same time
  (± 1 h), or become a single window when there is no reading. On Team they carry no
  percentage, so they change nothing.

### Codex: `account/rateLimits/read` (official, not verified live)

- learn.chatgpt.com/docs/app-server and the protocol types in openai/codex
  (`codex-rs/app-server-protocol/src/protocol/v2/account.rs`): one `initialize`
  (`clientInfo.name`/`version` required) then `initialized` per connection ("Requests
  sent before initialization receive a `Not initialized` error"), then
  `account/rateLimits/read` without params. Not experimental; no message reaches a model.
- Result: `rateLimits` (the `codex` limit) and `rateLimitsByLimitId` (one snapshot per
  metered limit, e.g. `codex_other`), each with `primary` / `secondary` windows of
  `usedPercent` (0–100), `windowDurationMins` and `resetsAt` (Unix **seconds**). Hedy
  reads the map when present, the window kind from its length, and names non-`codex`
  limits by `limitName` / `normalModelSlug`. Without a ChatGPT login it errors
  ("chatgpt authentication required to read rate limits"): shown as "no se pudo leer".
- Run as `codex app-server --listen stdio://` with the account's `CODEX_HOME`, 20 s

### Cache and refresh

- One row per account in `plan_usage` (last reading as JSON, last attempt, why it
  failed). Screens read the cache only; a failed attempt keeps the last reading and the
  UI shows a muted note ("no se pudo actualizar").
- A new reading is asked at most every 3 min per account
  (`PLAN_USAGE_MIN_INTERVAL_SECS`); the attempt is recorded before asking, so the app's
  screens and the CLI do not run the same command twice.
- The app asks (never blocking the UI) when the shell appears or the screen changes,
  every 5 min while the window is focused, on focus, and when a task stops running.
  `hedy status` refreshes in parallel with the login checks (spinner); `hedy doctor`
  only reports from the cache.
- Compact labels (header chips, sidebar) use the shared window closest to its limit
  (usually the session, the week when it is the one about to stop the work). Colors:
  ≥ 80 % warning, ≥ 95 % danger (bar fill and the percentage), never the account color
  as text.

## 22. Accepting after a review, undo, and waiting for a limit (Nov 14, 2026)

### Review before accepting

- "Aceptar cambios" opens a sheet first (`Hedy::accept_preview`, nothing changes): target
  branch and task branch, files and +/− lines, the branch the main folder is on (warned
  when it is not the target), the task's latest `TestsRun` (passed, failed or none; a
  failure or no tests is a warning, never a block) and an editable commit message. The
  proposal is the task's title plus the first paragraph of the agent's last summary
  (≤ 300 chars, `domain::task::default_commit_message`); empty falls back to it. Before,
  the message was the title alone.
- In the diff, `j` / `k` move between files (not while typing in a field) and each file
  can be marked "Revisado" ("3 de 7 revisados"). The marks are per task and per file
  version (path + counts), in the webview's `localStorage`: a convenience, never sent
  anywhere.

### Undo (strategy and limits)

- Accepting stores a `MergeRecord` in the task: base branch commit before and after the
  merge (a merge commit or a fast-forward) and the task branch's tip.
- "Deshacer" (a 12 s toast after accepting, and "Deshacer la integración" on the accepted
  task) only acts when all of this holds; otherwise it refuses and says why
  (`UndoBlocked`), suggesting `git revert`:
  1. the main folder is on the base branch;
  2. the base branch is still at the merge (`HEAD == after`): no commits after it;
  3. no remote-tracking branch contains the merge (`git branch -r --contains`): never
     rewrites pushed history;
  4. `git reset --keep <before>` succeeds: git itself refuses when a file the merge
     changed has local changes, and leaves other local changes and untracked files alone.
- The task's branch and worktree are re-created at the tip **before** the reset (and
  removed again if the reset is refused), so the work is never lost; the task goes back
  to "Lista para revisar" and can be accepted again.
- Why not `git revert -m 1`: it works after other commits, but it adds commits, and a
  reverted merge cannot simply be merged again later (git sees the commits as already
  merged), so "back to review" would not work. Reset-only-when-nothing-else-happened is
  the safest option that keeps undo exact; anything else stays the user's call.
- Tasks accepted before this change have no record and cannot be undone from Hedy.

### Waiting for a limit

- "Esperar" stores a `LimitWait` in the task (account, reset time, since, `ready`). Tasks
  are stored as JSON, so this is a task field with `#[serde(default)]`: **no SQLite
  migration**; `waiting_tasks()` filters on `json_extract(data, '$.wait')`. The reset time
  is the latest reached-limit report of that account in the task (`resetsAt`), else the
  latest renewal among the plan-usage windows at 100 % (§20), else the last
  `rate_limit_event`; only future times count. Unknown → no countdown and the user
  presses "Continuar".
- While the app runs, a thread calls `Hedy::resume_due_waits` every 15 s. A due task
  resumes **on the same account** (rule 3): if its account or current phase's account is
  no longer the one waited for (a handoff), nothing is sent. It sends the held queue
  (§19), or "Tu límite se renovó. Continúa con la tarea donde la dejaste.", as the next
  turn of the same session (resumed with its session id if the process is gone; queued
  if a turn is still running), clears the session's limit memory so a new limit warns
  again, and notifies ("Claude sigue con la tarea · proyecto"). If it cannot start, the
  queue goes back on hold, the error is in the history and the wait becomes `ready`.
- If the reset passed while Hedy was closed, start-up only marks the wait `ready`
  (`mark_overdue_waits`) and notifies "Ya puedes continuar": nothing is sent without the
  user there (tokens are spent only when someone can watch). The card then shows
  "Continuar".
- Writing to the agent, a handoff, accepting or "Cancelar espera" end the wait. The other
  options on the card (hand over to another provider or an API key) stay as they were.
- The limit card counts down every second (outside the timeline's live region, so
  screen readers are not flooded); the Activity board row says "sigue en 47 min" or
  "ya puede continuar".
- **Not verified live**: a real reset with a real account (tested with the agent double,
  the fake clock and `MockApi`).

## 23. Projects from scratch and quick questions outside any project (Nov 14, 2026)

### New project ("Nuevo proyecto", `hedy new <name> [--in <parent>] [--account <id>] [--protect]`)

- `Hedy::new_project` checks everything **before** creating anything: the name gives a
  safe folder (`domain::project::folder_name`: accents folded, lowercase letters, digits,
  `-`, `_`, `.`, at most 64 chars, at least one letter or digit: "Mi tienda online" →
  `mi-tienda-online`); the parent is an absolute path; the folder does not exist; the
  parent is writable (when it exists; a missing parent such as `~/Proyectos` is created);
  the account (given, else the default one) passes the protection rules (a reserved
  account is refused; a protected project cannot use the default account).
- Then `FileSystem::create_new_dir` (`create_dir`, which fails on an existing path: never
  overwrites), and `Git::init_repo`: `git init` (the user's own default branch name and
  identity) plus **one empty commit**, "Initial commit". Tasks fork worktrees from
  `HEAD`, which needs a commit; an empty one writes no file the user did not ask for (no
  README). If git fails (typically no `user.name`/`user.email`: the message says how to set
  them), the folder just created is removed again. Then the project is registered with
  the name as typed, its account, protection and client.
- The default parent (`default_project_parent`): where most registered projects live;
  else the first existing of `~/Proyectos`, `~/Projects`, `~/projects`, `~/code`, `~/Code`,
  `~/dev`, `~/src`; else `~/Proyectos` (`~/Projects` in English).
- In the app, the dialog asks only for the name and shows the folder ("Cambiar…" uses the
  folder picker) and the final path, checked live (`new_project_path`, which creates
  nothing). Account (preselected: the default one if allowed), protection and client are
  under "Más opciones". There is no "first request" field: after creating, the app opens
  the project's composer for a new task, focused, with Proyecto mode and "Planificar
  primero" as usual — one composer, not a second one in a dialog.
- "Agregar proyecto" (an existing folder) is now worded "Abrir carpeta…".

### Quick questions ("Pregunta rápida"): conversations

- **Model:** a conversation is a normal `Task` with `conversation: true` (a JSON field
  with `#[serde(default)]`: no migration; `conversations()` filters on
  `json_extract(data, '$.conversation')`). Its `project` is its own scratch folder,
  `<data dir>/chats/<task id>/`, created private (0700, like account folders). So
  everything that works on tasks works unchanged: the cwd is `Task::work_dir()`, the
  permission rules deny writes outside it, follow-ups resume the same session, the queue,
  limits, waits and handoffs work, events and usage are recorded per account. Rejected
  alternatives: `project: Option<PathBuf>` (touches every use of a task, the store and the
  UI for one case) and a built-in "Conversaciones" project (it would be offered in every
  project list, have an account, phases and protection, and share one folder).
- Only `Ask` and `Research` (`ConversationChangesFiles` otherwise), one stage, no plan,
  **no workspace** (even for Codex and ACP agents, which always get a worktree in a
  project: the scratch folder is already empty, so there is nothing of the user's to
  read). The CLI's edit tools stay disabled as in any read-only task.
- **Account:** the one the user picks, else the default one; never another by itself
  (rule 3). Accounts reserved by a protected project are not offered nor accepted
  (`conversation_accounts`, `check_launch(None, …)`). Handoffs use a stand-in project
  without account or protection, so only the other projects' rules apply.
- **Memory and code map:** none. No memory MCP server (its tools are scoped to a project;
  a conversation would read nothing and propose notes with no project to belong to) and
  no code map (nothing to map). Global notes are not served either; to change that, the
  memory server would need a global-only mode.
- **Where they show:** the Activity board, "Últimas tareas", notifications and the palette
  name them "Conversación" instead of a project; the usage summary adds them up as one
  "Conversaciones" row with no client (the tokens also count in each account's usage as
  always). Deleting one (`delete_conversation`) stops its session, deletes the task with
  its events and queue, and removes its scratch folder — only when the task is a
  conversation and the folder is its own `chats/<id>`. Usage records stay.
- **UI:** one mental model, "a task belongs to a project or to no project": the same
  workspace screen with no project (`#c`, `#c=<id>`), without the changes panel, with the
  modes Pregunta/Investigar and an account picker in the composer bar (preselected), and
  Enter sends (Shift+Enter for a new line; in projects it stays Ctrl/⌘+Enter, as prompts
  there are longer). Entry points: home's single "Nuevo…" menu (Nuevo proyecto, Abrir
  carpeta…, Pregunta rápida), the sidebar's "+" next to "Proyectos" and "Conversaciones"
  (the last five, "Ver las N" for the rest), and the palette, where whatever was typed can
  be asked ("Preguntar «…»", which opens the question with that text, ready to send).
- **Not verified live:** a real conversation with each provider in an empty folder
  (tested with the agent double, temp folders and `MockApi`).

## 24. Images, file mentions and suggestions in the composer (Nov 15, 2026)

### Images with a prompt

- **What the user attaches.** PNG, JPEG, GIF or WebP, at most 5 MB each and 4 per message
  (`domain::attachment`). The type comes from the file's first bytes, never from its name
  or what the webview says; SVG is refused (Kimi refuses it too). The composer takes them
  from the paperclip button, a paste (Ctrl+V) or a drop.
- **Where they live.** The UI sends them base64 in the command; the backend checks them
  before anything is created and writes them to `<data dir>/attachments/<task id>/`
  (folder 0700, files 0600, never overwritten), never into the repository. The
  `UserMessage` event and the task (`Task::images`, for later phases and handoffs) keep
  only the name, the stored file name and the type. The timeline loads each thumbnail
  with `attachment(task, file)`, which only reads a name Hedy gave inside a real task's
  folder; a deleted file shows a placeholder and the history still loads. Deleting a
  conversation deletes its images.
- **How each agent gets them** (official input only; `AgentLauncher::image_support`):

  | Agent | Format | Source |
  |---|---|---|
  | Claude Code (`-p --input-format stream-json`) | the user message's `content` becomes `[{"type":"text"}, {"type":"image","source":{"type":"base64","media_type","data"}}]` | Agent SDK "Streaming Input" (code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode): image uploads are a streaming-input feature |
  | Codex app-server | `turn/start` `input: [{"type":"text"}, {"type":"localImage","path"}]` (the app-server reads the file) | learn.chatgpt.com/docs/app-server.md (input items `text`, `image` with `url`, `localImage` with `path`) |
  | ACP agents | `session/prompt` blocks `{"type":"image","mimeType","data"}`, only when `initialize` answered `agentCapabilities.promptCapabilities.image: true` (omitted = unsupported); otherwise only the text goes and the chat says so | agentclientprotocol.com/protocol/content and /initialization |
  | Kimi / Gemini by API key | a user message with `[{"type":"text"}, {"type":"image_url","image_url":{"url":"data:<type>;base64,…"}}]` | platform.kimi.ai K3 quickstart (base64 or `ms://`, no public URLs); Gemini's OpenAI compatibility ("image understanding") |

- **When an agent takes none.** An account whose adapter says no (today only an API account
  without its key, since it cannot work at all) gets the attach control disabled with the
  reason; the use cases refuse images for it (`ImagesNotAccepted`). A later phase or a
  handoff to such an agent gets a line saying the user attached N images it cannot see.
- **Queue.** Images never wait in the queue (`ImagesWhileQueued`): the queue is plain text
  in SQLite and joins messages into one turn. While the agent works, attaching is disabled
  with the reason.
- **Not verified live** (no tokens spent): the shapes are tested against fakes of each
  protocol (a recording `claude` stdin, a fake app-server, a fake ACP agent with and
  without the capability, a local HTTP server). Which ACP CLIs advertise images
  (Gemini CLI, Kimi Code, Antigravity) is not checked: none is installed here.

### `@file` mentions

- Typing `@` in a project's composer lists the project's files (`Hedy::project_files`, the
  `Git::list_files` port): `git ls-files -z --cached --others --exclude-standard` in the
  main checkout, so tracked files plus untracked ones git does not ignore, never
  `.hedy/`. Protected names (`permissions::DEFAULT_BLOCKED`: `.env`, `.env.*`, keys,
  credentials…) are never offered, the same rule that keeps agents away from them.
  Sorted and cut at 5,000 paths (`MAX_PROJECT_FILES`).
- The picker ranks file names that start with the query, then names that contain it, then
  paths that contain it (no case), shorter paths first; ↑/↓, Enter or Tab insert
  `@relative/path `, Esc closes it. The mention is plain text in the prompt: each agent
  reads the file with its own tools, under Hedy's rules. A quick question has no project,
  so `@` is just text there.

### Suggestions in an empty task

- Under the mascot of a new project task: three ghost chips from what Hedy already knows
  locally (`project_status`, no agent and no network): failing tests from the last run
  any task saw, then a review of uncommitted changes, then always "explain how this repo
  is organized", then "add tests" and "find dead code" as fillers. The review is offered
  only with Claude Code, and switches the composer to Pregunta: Codex, ACP and API agents
  always work in a worktree forked from `HEAD`, where uncommitted changes do not exist.
- In a quick question: three generic starters with the caret placed where the user types.
- A chip fills the composer (and its mode); it never sends. They go once the task exists.
