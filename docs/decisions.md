# Decisions — Phase 0 (validation)

Verified on November 13, 2026 on Linux (CachyOS, fish).

| CLI | Version tested |
| --- | --- |
| Claude Code | 2.1.306 |
| Codex | 0.169.0 |
| Gemini CLI | 0.68.0 |

Sources: current official docs, each binary's `--help`, the JSON Schema generated by
`codex app-server`, and the prototypes in `prototypes/phase0`. Anything not officially
documented is marked **unverified**.

> These CLIs change almost weekly. Hedy must record each binary's version and warn when
> it changes (`hedy doctor`). This document holds for the versions in the table.

---

## 1. Recommendation: mixed mode

| Provider | Hedy chat (events + approvals) | Terminal tab and `hedy run` |
| --- | --- | --- |
| Claude Code | `claude -p` with stream-json both ways | interactive `claude` in a PTY |
| Codex | `codex app-server` (JSON-RPC over stdio) | interactive `codex` in a PTY |
| Gemini ⚠️ | `gemini --acp` (Agent Client Protocol) | interactive `gemini` in a PTY |
| Kimi / Gemini API | OpenAI-compatible HTTP (`reqwest`) | — |

⚠️ Gemini CLI **no longer accepts personal Google accounts** (see section 5): it only
works with Code Assist Standard/Enterprise or a paid API key.

**Why mixed:**

- Hedy's own chat needs structured events and has to **ask for approval** before every
  command or edit. The three chosen modes let Hedy answer those requests; a PTY only
  gives screen text that cannot be translated reliably.
- The PTY is still needed: it is where the user does each CLI's **official login** the
  first time (each CLI shows its own wizard), and it is what `hedy run` uses.
- All three structured protocols belong to the official, unmodified CLIs.

**Why not ACP for everything:** Gemini speaks ACP natively, but Claude Code and Codex only
do it through third-party adapters (`claude-agent-acp`, `codex-acp`), which add another
layer and another binary. Their native protocols are more direct. If more ACP CLIs are
added later (Kimi Code, for instance), the Gemini ACP adapter is reused.

## 2. Account separation by folder

| CLI | Variable | Where the login lives (Linux) | Check without reading tokens |
| --- | --- | --- | --- |
| Claude Code | `CLAUDE_CONFIG_DIR` | `$CLAUDE_CONFIG_DIR/.credentials.json` (0600) | `claude auth status --json` (exit 0 = logged in, 1 = not) |
| Codex | `CODEX_HOME` (folder must exist) | `$CODEX_HOME/auth.json` with `cli_auth_credentials_store = "file"` | `codex login status` (exit 0 / 1) or app-server `account/read` |
| Gemini | `GEMINI_CLI_HOME` (creates `.gemini/` inside) | `$GEMINI_CLI_HOME/.gemini/oauth_creds.json` | No command. `google_accounts.json` holds the active email (no tokens) |

Tested with empty folders: each CLI wrote only inside its folder and did not touch
`~/.claude`, `~/.codex` or `~/.gemini`.

### Claude Code

- `CLAUDE_CONFIG_DIR` is documented (code.claude.com/docs/en/env-vars): it relocates
  settings, history, plugins, credentials, and also `.claude.json`.
- **Important detail:** without the variable Claude uses `~/.claude/` **and**
  `~/.claude.json` (outside the folder). With the variable it looks for
  `$CLAUDE_CONFIG_DIR/.claude.json`. So the existing account must **not** be "adopted"
  by setting `CLAUDE_CONFIG_DIR=~/.claude`: it would lose the MCP servers and settings in
  `~/.claude.json`. The existing account is registered in Hedy as the "default folder"
  and launched **without** the variable.
- On this machine the default account (`~/.claude`) is a **Team** subscription (work).
- Login into a new folder: `CLAUDE_CONFIG_DIR=<folder> claude auth login` (or `/login`
  inside `claude`). Both are the official flow.
- `claude auth status --json` returns `loggedIn`, `authMethod`, `subscriptionType`,
  `configDirectory`, and also email and organization. Hedy stores only what it needs.
- Doc caveat: two **Claude Console sign-ins without an API key** are not separated by
  folder. This does not affect subscription accounts.

### Codex

- `CODEX_HOME` is documented (learn.chatgpt.com/docs/config-file/environment-variables):
  config, auth, logs, sessions and skills.
- The login may go to `auth.json` or to the OS keyring. How the keyring entry is keyed per
  folder is **not documented**, so Hedy forces `cli_auth_credentials_store = "file"` in each
  account's `config.toml`. Codex writes and reads that file; Hedy never opens it.
- Login: `CODEX_HOME=<folder> codex login` (browser) or `codex login --device-auth`.

### Gemini

- `GEMINI_CLI_HOME` is documented (geminicli.com/docs/cli/enterprise and the bundled
  `docs/reference/configuration.md`).
- By default the Google login is stored in `oauth_creds.json` inside the folder.
- **Risk found in the code:** with `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE=true` the login
  goes to the keyring under service `gemini-cli-oauth` with a **fixed key**
  (`main-account`), the same for every folder. Two accounts would overwrite each other.
  Hedy removes that variable from the environment.

### Variables Hedy always removes (enforced in code)

If any of these reach the child process, the CLI uses that credential instead of the
folder's login, or bills through the API without warning:

- Claude: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`.
  The docs say that in `-p` mode the API key "is always used when present".
- Codex: `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`.
- Gemini: `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GENAI_USE_VERTEXAI`,
  `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE`.
- Leftovers from the session that launched Hedy: `CLAUDECODE`, `CLAUDE_CODE_*`,
  `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GEMINI_CLI_HOME`. Hedy then sets the variable for
  the selected account.

## 3. Claude Code

### Headless mode

```
claude -p --input-format stream-json --output-format stream-json --verbose \
       --permission-prompt-tool stdio --permission-mode manual [--model <alias>]
```

- Input (stdin, one line per message):
  `{"type":"user","message":{"role":"user","content":"..."},"parent_tool_use_id":null,"session_id":""}`.
  The process stays alive and accepts more messages; closing stdin ends it.
- Output: `system` (`init`, `compact_boundary`, `api_retry`, `status`, hooks…),
  `assistant`, `user` (tool results), `stream_event` (with `--include-partial-messages`),
  `rate_limit_event`, `result`, and `control_request` / `control_response`.
- `result` has `subtype` (`success`, `error_max_turns`, `error_during_execution`,
  `error_max_budget_usd`…), `is_error`, `duration_ms`, `num_turns`, `usage`, `modelUsage`,
  `total_cost_usd` and `permission_denials`. `total_cost_usd` is a **client-side
  estimate**; the docs warn it may not match the bill.
- Useful flags: `--resume <id>`, `--session-id <uuid>`, `--fork-session`,
  `--mcp-config` + `--strict-mcp-config`, `--append-system-prompt`, `--max-budget-usd`,
  `--include-hook-events`, `--no-session-persistence`.
- `--permission-mode` accepts `default` (alias `manual`), `acceptEdits`, `plan`, `auto`,
  `dontAsk` and `bypassPermissions`. `plan` fits the "plan" phase.

### Approvals: three routes

1. **Control protocol over stdio** (`--permission-prompt-tool stdio`). Claude sends a
   `control_request` with `subtype: "can_use_tool"`, `tool_name` and `input`. Hedy answers
   with a `control_response` `{"behavior":"allow","updatedInput":…}` or
   `{"behavior":"deny","message":…}`. The official Agent SDK uses it. Tested: the
   `initialize` handshake answers. **Risk:** only partly documented (no public spec).
2. **MCP permission tool** (`--permission-prompt-tool mcp__hedy__approve`). Officially
   documented: the tool returns one text block with `{"behavior":"allow"}` or
   `{"behavior":"deny","message":"…"}`. Requires Hedy to serve a small MCP (it will need
   one for memory anyway).
3. **`PermissionRequest` hook.** Documented, works in `-p`.

**Proposed decision:** use route 1 and keep route 2 as a fallback behind the same port.
If an update breaks route 1, it is swapped without touching the UI. "Allow for this chat"
is remembered by Hedy per session.

### Usage and limits

- `rate_limit_event` in the stream: `status` (`allowed`, `allowed_warning`, `rejected`),
  `resetsAt` and `utilization`. The docs do not say which window (5 h or weekly)
  `utilization` refers to. **Unverified** with a real account yet.
- The `statusLine` command receives `rate_limits.five_hour` and `rate_limits.seven_day`
  with percentage and reset time, only on Pro/Max/Ultra and after the first response.
  Option for PTY sessions: Hedy registers its own `statusLine` command (via `--settings`)
  that only records those percentages.
- No rate-limit metrics via OpenTelemetry.

### Does programmatic use draw from a different pool? (phase 0 question)

Source: support.claude.com/en/articles/15036540 ("Use the Claude Agent SDK with your Claude plan").

- **June 15, 2026:** Anthropic **paused** the announced change: "Claude Agent SDK,
  `claude -p`, and third-party app usage still draw from your subscription limits."
- **October 7, 2026:** Max, Ultra and Team plans include monthly API credits. Those credits
  only apply when the SDK or `claude -p` run with an **API key** from the linked Console
  organization. With a subscription login, `claude -p` still draws from plan limits.
- **Conclusion:** today `claude -p` with a subscription login draws from the **same pool**
  as interactive use. Headless and PTY cost the same.
- The credit amounts are **unverified** (not in the article).
- This changed twice this year; Hedy will show the source on the accounts screen and we
  re-check it every phase.

### Policy note

The Agent SDK docs say: "Unless previously approved, Anthropic does not allow third party
developers to offer claude.ai login or rate limits for their products." Hedy is a
**personal, local** tool that launches the official binary with the login the user did
themselves; it does not offer claude.ai login to third parties. If it is ever distributed
to other people, this must be reviewed first.

## 4. Codex

Docs moved from `developers.openai.com/codex` to `learn.chatgpt.com/docs`.

### App server (recommended for the chat)

- `codex app-server --listen stdio://`: JSON-RPC 2.0, one JSON line per message. OpenAI
  presents it as "the interface Codex uses to power rich clients". Marked experimental;
  without `capabilities.experimentalApi` the client stays on the stable surface.
- Flow: `initialize` → `initialized` notification → `thread/start` (`cwd`,
  `approvalPolicy`, `sandbox`, `model`) → `turn/start` (`threadId`,
  `input: [{type:"text", text}]`).
- Notifications: `item/started`, `item/completed` (types `agentMessage`, `plan`,
  `reasoning`, `commandExecution`, `fileChange`, `mcpToolCall`…),
  `item/agentMessage/delta`, `turn/plan/updated`, `turn/diff/updated`,
  `thread/tokenUsage/updated`, `account/rateLimits/updated`, `turn/completed`, `error`.
- **Approvals:** the server sends `item/commandExecution/requestApproval` and
  `item/fileChange/requestApproval`. Answers `accept` / `acceptForSession` / `decline` map
  1:1 to **Allow / Allow for this chat / Deny**.
- **Limits:** `account/rateLimits/read` returns `primary` and `secondary`, each with
  `usedPercent`, `windowDurationMins` and `resetsAt`. Hedy reads `windowDurationMins`
  instead of assuming which window is 5 h and which is weekly.
- `codex app-server generate-json-schema --out <dir>` generates the exact schema for that
  version. Hedy will pin the supported version and generate Rust types from it.
- Tested: `initialize` and `account/read` work without login (`requiresOpenaiAuth: true`);
  `account/rateLimits/read` returns "authentication required".

### Alternative: `codex exec --json`

JSONL with `thread.started`, `turn.started`, `item.*`, `turn.completed` (with `usage`),
`turn.failed` and `error`. Good for single-turn jobs, but it **cannot ask for approvals**
(fixed policies only) and has no limits. `--full-auto` no longer exists.

### Billing

"Local messages and cloud chats share your plan's usage allowance." No separate pool is
documented for `exec` or the app server; everything points to the same one.

## 5. Gemini

### ⚠️ Gemini CLI no longer works with personal accounts

- Since **June 18, 2026**, Gemini CLI stopped serving consumer accounts: free tier,
  Google AI Pro and Google AI Ultra. Google replaced it with **Antigravity CLI** (`agy`).
  Sources: developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli
  (May 19, 2026) and the banner on every geminicli.com page. The 0.68.0 binary itself
  contains messages pointing to Antigravity CLI.
- **Still works** with Gemini Code Assist Standard/Enterprise and paid Gemini API keys.
  Vertex AI and free API keys: **unverified** (sources conflict).
- **Antigravity CLI** has `agy acp`, but it stores the login in the **OS keyring** and has
  no documented variable to relocate its folder. That rules out several accounts separated
  by folder: for now it only fits **one personal account** per machine.
- Gemini CLI is still maintained (0.68.0 on Nov 10; 0.69 in preview).

### What was verified about Gemini CLI

- Official package `@google/gemini-cli` (0.68.0). Login: "Log in with Google"
  (`oauth-personal`), Gemini API key, or Vertex AI.
- **ACP** (`gemini --acp`; `--experimental-acp` is deprecated): JSON-RPC over stdio.
  Methods `initialize` (returns `authMethods`), `authenticate`, `session/new`,
  `session/load`, `session/prompt`, `session/cancel`, `session/set_mode`. The agent sends
  `session/update` notifications (`agent_message_chunk`, `tool_call`, `tool_call_update`,
  `plan`…) and asks for approval with `session/request_permission`, offering
  `allow_once` / `allow_always` / `reject_once`. They map 1:1 to Hedy's approval cards.
- Tested: `initialize` returns the auth methods; `session/new` without login returns
  "Gemini API key is missing or not configured".
- **Headless** (`gemini -p … -o stream-json`): events `init`, `message`, `tool_use`,
  `tool_result`, `error`, `result` (with per-model stats), all with `type` and
  `timestamp`. It cannot ask for approvals, only `--approval-mode` (`default`,
  `auto_edit`, `yolo`, `plan`). Fits `hedy ask`. Exit codes: 0, 1 (error), 42 (bad
  input), 53 (turn limit).
- In a PTY, the first run shows "Waiting for authentication…" (may open the browser) and
  the trust-folder question.
- **Quota:** 1,500–2,000 requests/day depending on the plan (Code Assist Standard /
  Enterprise). There is no programmatic way to read the remaining quota (`/stats model`
  is interactive only). Hedy will count requests and show it as an **estimate**.
- MCP: `mcpServers` in `settings.json` or `gemini mcp add --scope user|project`. The context
  file can be renamed with `context.fileName` (e.g. to `AGENTS.md`).
- **Terms:** using the Code Assist service with Gemini CLI's login from third-party
  software (i.e. bypassing the CLI) is prohibited and may lead to suspension. Launching the
  official, unmodified CLI, as Hedy does, is not prohibited, though not explicitly allowed.

### Gemini through the API (Kimi-style provider)

- OpenAI-compatible endpoint: `https://generativelanguage.googleapis.com/v1beta/openai/`
  with `Authorization: Bearer <GEMINI_API_KEY>`. Supports `tools`, `stream` and
  `stream_options.include_usage`. Google still labels it beta.
- Coding models: `gemini-4-carbon` ("built for complex software engineering"),
  `gemini-4-hydrogen` ("everyday coding and agentic workflows") and `gemini-3.8-flash`.
  The 2.5 family is retired on December 1, 2026.
- Gemini then works like Kimi: an API key in the keyring and the shared HTTP adapter.
  **This is the simplest and safest way to add Gemini with a personal account.**

## 6. Kimi

- Docs moved to `platform.kimi.ai` (formerly `platform.moonshot.ai`).
- OpenAI-compatible API: `POST https://api.moonshot.ai/v1/chat/completions` (China:
  `api.moonshot.cn`). Supports `tools`, `stream` and `stream_options.include_usage`
  (total usage in the last chunk).
- **Current models:** `kimi-k3.1-pro` (most capable, 1M context),
  `kimi-k3.1-pro-highspeed` and `kimi-k3`. The `kimi-k2.*` family is deprecated or retires
  in December 2026. K3 models always "think" and take `reasoning_effort`.
- There is also an Anthropic-compatible endpoint (`https://api.moonshot.ai/anthropic`).
- **Kimi Code** (subscription) has its own endpoints and keys
  (`https://api.kimi.ai/coding/v1`) and a new official CLI, `MoonshotAI/kimi-code`, which
  speaks ACP (`kimi acp`). The old `kimi-cli` is archived.

## 7. PTY (`portable-pty`)

- Works with all three CLIs. On first run each shows its wizard: Claude asks for a theme
  and then login, Codex offers "Sign in with ChatGPT / Device Code / API key", and Gemini
  asks for login and folder trust.
- Hedy **does not automate** those wizards: the user logs in from the Terminal tab. That
  keeps rule 1.
- `portable-pty` starts in `$HOME` unless told otherwise: always pass `cwd`.
- PTY session state is not read by scraping the screen. Claude hooks and `statusLine`
  write to a Hedy socket instead.

## 8. Changes from the original spec

1. **Gemini** added as a provider (requested during phase 0). Gemini CLI only works with
   Code Assist Standard/Enterprise or a paid API key. For a personal account, the practical
   route is the Gemini API over HTTP, like Kimi.
2. **Kimi:** model names changed to `kimi-k3.x`. Two ways to use it: API (pay as you go)
   or Kimi Code (subscription, with official CLI and ACP).
3. **Codex:** recommended mode is the app server, not `exec`, because `exec` cannot ask for
   approvals.
4. **Claude:** chat approvals rely on a partly documented protocol. Mitigation: fallback to
   the MCP permission tool.
5. **Anthropic policy** on claude.ai login in third-party products: no effect while Hedy is
   for personal use.
6. **Protected projects (rule 4)** are now **opt-in per project and off by default**
   (user decision, Nov 13, 2026). No account is ever blocked by default; when a project is
   marked protected, it only uses its assigned account and that account is not offered
   elsewhere.
7. **Language:** code, identifiers, folders, docs and commits in English. User-facing text
   stays in Spanish.

## 9. Decisions

- **Claude accounts:** `~/.claude` (Team) is registered as the default-folder account and
  launched without `CLAUDE_CONFIG_DIR`. New accounts live in Hedy folders.
- **Folders:** accounts in `~/.local/share/hedy/accounts/<id>/` (XDG data), Hedy config in
  `~/.config/hedy/`.
- **Open:** Kimi (API, Kimi Code subscription, or both) and Gemini (API key, Code Assist,
  or Antigravity for a personal plan). Both arrive in phase 4.
- **Pending:** end-to-end test with a real login (see `prototypes/phase0/README.md`).
